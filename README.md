# pm-smartfactory

IT/AI·스마트팩토리 프로젝트에서 **Claude Code를 PM/PL 보조로 쓰기 위한 Claude Code 플러그인.**

일정·요구사항·DB검증·회의록·산출물검수·리스크 절차를 **skill 10개**로 제공하고,
항상 지켜야 하는 제약(협업 원칙·응답 규칙·산출물 포맷·보안)만 `CLAUDE.md` 템플릿(135줄)으로 남긴다.

> **왜 이 구조인가**
> v2까지는 863줄짜리 `CLAUDE.md` 하나였다. 회의록만 정리하는 세션에도 SQL 리뷰 체크리스트와
> 문서 검수 항목이 전부 컨텍스트에 올라갔다. 토큰 낭비보다 큰 문제는 **지시 희석**이다.
> 규칙이 100개 나열되면 모델이 전부를 균일하게 따르지 못한다.
> v3는 **"항상 켜져 있어야 하는 것"과 "필요할 때만 꺼내는 것"을 분리**했다.

## 1. 설치 (최초 1회)

Claude Code 세션 아무 곳에서나 실행한다. **프로젝트 폴더가 아니어도 된다.**

```
/plugin marketplace add weaseleyegun/Project-Management-with.-Claude-
```
```
/plugin install pm-smartfactory
```
scope 설정: user (전역)

설치 확인:

```
/plugin
```

→ `pm-smartfactory` 가 목록에 보이면 완료. 이제 **모든 프로젝트에서** skill 10개와 커맨드 3개를 쓸 수 있다.

### 개인 프로필 등록 (권장, 1회)

`templates/personal-profile.example.md`의 내용을 본인에 맞게 고쳐
`~/.claude/CLAUDE.md`(Windows: `C:\Users\<사용자>\.claude\CLAUDE.md`)에 붙여넣는다.

소속·역할·기술스택·성향을 알려주면 기초 개념 설명을 생략하고 설계 판단 중심으로 답한다.
**개인 정보이므로 프로젝트 저장소에는 넣지 않는다.**

### 업데이트

이 저장소가 갱신되면:

```
/plugin marketplace update pm-smartfactory-marketplace
```

**프로젝트마다 파일을 복사해 다닐 필요가 없다.** v2에서 가장 번거로웠던 부분이다.
다만 각 프로젝트의 `CLAUDE.md`는 복사본이므로, 템플릿이 바뀌면 `/init-project`가 차이를 알려준다.

## 2. 시나리오 A — 신규 프로젝트 시작하기

착수보고 전, 아직 아무것도 없는 상태에서 시작하는 경우.

### A-1. 폴더 만들고 Claude Code 실행

```powershell
mkdir "D:\projects\2026_OO공장_실증"
cd "D:\projects\2026_OO공장_실증"
claude
```

### A-2. 온보딩 인터뷰

```
/init-project
```

이때 일어나는 일:

| 단계 | 내용 |
|---|---|
| 0 | 플러그인 템플릿에서 `CLAUDE.md`를 이 폴더로 복사 |
| 1 | 기존 `PROJECT.md` 확인 (없으니 전체 질문) |
| 2 | **21개 항목을 한 번에** 제시 — 하나씩 되묻지 않는다 |
| 3 | 답변으로 `PROJECT.md` 생성 |
| 4 | `.env` 점검 · `.gitignore` 경고 |
| 5 | 표준 폴더 구조 생성 여부 확인 |
| 6 | 상시 리스크 11개 중 해당 항목을 `PROJECT.md` §10에 초기 등재 |
| 7 | 미사용 모듈 표시 (공유드라이브 안 씀 / DB 없음 등) |

**모르는 건 답하지 않아도 된다.** `<TBD>`로 남고, 나중에 그 정보가 실제로 필요한 작업을 할 때 그때 묻는다.
"지금은 건너뛰자"고 하면 빈 `PROJECT.md`만 만들고 바로 일을 시작한다.

> **사업계획서(제안서)가 있으면 3번 질문에서 경로를 알려주는 게 가장 이득이 크다.**
> 예산·KPI·마일스톤·수행기간(§1, §6, §9)을 직접 읽어서 채운다. 손으로 옮길 필요가 없다.

### A-3. 결과 확인

```
D:\projects\2026_OO공장_실증\
├─ CLAUDE.md      ← 상시 제약 135줄 (플러그인 템플릿 복사본)
├─ PROJECT.md     ← 이 프로젝트 고유 값
├─ 01_기획/ 02_요구사항/ ... (표준 폴더)
```

### A-4. 바로 일 시작

```
> 착수보고 기준으로 WBS L1 구성부터 잡아줘
```

→ `wbs-progress` skill이 자동으로 걸리고, L1만 먼저 제안한 뒤 승인을 기다린다(순차 진행 원칙).

## 3. 시나리오 B — 이미 진행 중인 프로젝트에 적용하기

**이쪽이 실제로 더 흔하다.** 요구사항정의서도 있고 회의록도 쌓여 있고 폴더 배치도 이미 굳어 있는 상태.

### 핵심 원칙: 기존 구조를 갈아엎지 않는다

`/init-project`는 표준 폴더 구조를 *제안*하지만, **이미 파일이 있으면 강제로 옮기지 않는다.**
실제 배치를 `PROJECT.md` §3에 그대로 기록하고, 새로 만드는 파일부터 점진 적용할지 물어본다.

### B-1. 기존 프로젝트 폴더에서 실행

```powershell
cd "D:\projects\진행중인_프로젝트"
claude
```

### B-2. 폴더 구조 생성은 거절한다

```
/init-project
```

- 21개 질문 중 **7번(로컬 작업 폴더)** 과 **8번(공유드라이브 경로)** 에 현재 실제 경로를 그대로 적는다.
- 5단계 "폴더 구조를 만들까요?" → **"아니오, 기존 구조를 유지한다"** 로 답한다.
- 그러면 실제 배치가 `PROJECT.md` §3에 기록되고, 이후 Claude는 그 경로 기준으로 움직인다.

### B-3. 이미 있는 산출물을 물려주기

인터뷰만으로는 진행 상황이 안 잡힌다. 이어서 이렇게 시킨다.

```
> 02_요구사항/ 아래 요구사항정의서 읽고, 현재 요구사항 건수랑
  인수 기준 누락 항목만 뽑아줘

> 01_기획/WBS_260721.xlsx 읽고 PROJECT.md 마일스톤 표(§9) 채워줘.
  실제 완료일 기준으로

> meetRecord/ 최근 3개 회의록 읽고 미결사항 중 아직 안 닫힌 것만 정리해줘
```

각각 `requirements` / `wbs-progress` / `meeting-notes` skill이 걸린다.
**즉시 반영 원칙**에 따라 결과가 `PROJECT.md`에 바로 반영된다.

### B-4. 프로젝트 고유 규칙을 §11에 넣는다

기존 프로젝트는 이미 자기만의 규약이 있다. 플러그인 기본값과 다른 건 전부 여기에 적는다.
**`PROJECT.md` §11이 `CLAUDE.md`와 skill보다 우선한다.**

```markdown
## 11. 프로젝트 고유 규칙

- 요구사항ID는 REQ-### 3자리 단순 체계를 이미 쓰고 있다. 플러그인 기본(FR-VIS-001)으로 바꾸지 않는다.
- 회의록은 사내 표준 docx 양식을 쓴다. md로 만들지 않는다.
- 공유드라이브 미사용. 동기화 비활성화.
- WBS 진척률은 고객사 요구로 5% 단위를 쓴다. 5단계 규칙 예외.
```

### B-5. 기존 `CLAUDE.md`가 이미 있다면

`/init-project`가 덮어쓰지 않고 **차이만 요약해서 보여준다.** 살릴 것만 골라 병합하면 된다.
직접 하고 싶으면 이렇게 시킨다.

```
> 지금 CLAUDE.md랑 플러그인 templates/CLAUDE.md 비교해서,
  지금 파일에만 있는 규칙 목록으로 뽑아줘. 어디로 가야 할지도 같이
```

→ 상시 제약이면 `CLAUDE.md`에 남기고, 절차면 `PROJECT.md` §11 또는 skill 재정의로 보낸다.

## 4. 시나리오 C — 여러 프로젝트를 동시에 운영하기

PM은 보통 2~4개를 병행한다. 이 구조는 그 상황을 전제로 설계됐다.

```
~/.claude/CLAUDE.md          ← 개인 프로필 (모든 프로젝트 공통, 1개)
플러그인 (설치본)             ← skill·커맨드 (모든 프로젝트 공통, 1개)

D:\projects\A공장\CLAUDE.md    ← 상시 제약 (동일 복사본)
D:\projects\A공장\PROJECT.md   ← A공장 고유 값        ← 여기만 다르다
D:\projects\B사_MES\CLAUDE.md
D:\projects\B사_MES\PROJECT.md ← B사 고유 값
```

- **프로젝트를 바꿀 때 하는 일: 폴더 이동뿐이다.** Claude Code가 그 폴더의 `CLAUDE.md`와 `PROJECT.md`를 자동으로 읽는다.
- 절차(skill)는 플러그인 한 곳에만 있으므로, 새 실패 패턴을 배우면 **한 번만 고치면 전 프로젝트에 반영**된다.
- 고객사명·경로·DB 접속정보가 프로젝트끼리 섞이지 않는다. 각 `PROJECT.md`에 갇혀 있다.

## 5. `/init-project`는 언제 쓰는가

| 상황 | 쓰나? | 이유 |
|---|---|---|
| 새 프로젝트 폴더를 막 만들었다 | ✅ **쓴다** | 본래 용도 |
| 진행 중인 프로젝트에 이 플러그인을 처음 적용한다 | ✅ **쓴다** | 폴더 생성만 거절 (→ [시나리오 B](#3-시나리오-b--이미-진행-중인-프로젝트에-적용하기)) |
| `PROJECT.md`에 `<TBD>`가 많이 남아 한 번에 채우고 싶다 | ✅ **쓴다** | `<TBD>` 항목만 골라서 재질문한다 |
| 사업계획서를 뒤늦게 받았다 | ✅ **쓴다** | 예산·KPI·마일스톤을 문서에서 읽어 채운다 |
| 담당자가 바뀌어 이해관계자를 갱신해야 한다 | ⚠️ 굳이 | `PROJECT.md` §2만 직접 고치면 된다 |
| 회의 결과를 반영하려 한다 | ❌ **안 쓴다** | `meeting-notes` skill이 자동으로 처리 |
| 새 요구사항이 추가됐다 | ❌ **안 쓴다** | 그냥 요청하면 `requirements`가 걸린다 |
| 매주 진척을 정리한다 | ❌ **안 쓴다** | `/weekly` 를 쓴다 |

> **한 줄 요약: `/init-project`는 "프로젝트의 정체성을 등록/갱신"할 때만 쓴다.**
> 일상 업무는 평소 말투로 요청하면 알아서 걸린다.

## 6. 폴더 구조

### 6-1. 프로젝트 폴더 (내가 일하는 곳)

`/init-project` 5단계에서 제안하는 표준 구조. **강제가 아니다.**

```
{프로젝트명}/
├─ CLAUDE.md          # 상시 제약 135줄. 매 세션 자동 로드
├─ PROJECT.md         # 이 프로젝트 고유 값. 공개 저장소 커밋 금지
├─ .env               # DB 접속정보. .gitignore 필수
├─ 01_기획/            # 사업수행계획서, WBS
├─ 02_요구사항/         # 요구사항정의서, 감리ID_추적표
├─ 03_설계/            # 시스템/DB/인터페이스 정의서, 화면 프로토타입(HTML)
├─ 04_개발/
├─ 05_시험/            # 단위/통합/성능 테스트 결과서
├─ meetRecord/        # 회의록
├─ 07_보고/            # 주간보고, 단계보고
├─ 08_데이터/
│   ├─ raw/           # 원본 불변 — 절대 덮어쓰지 않는다
│   ├─ processed/
│   └─ analysis/
├─ _scratch/          # .py, .sql, 덤프 — 공유드라이브 동기화 제외
└─ 99_참고/
```

**왜 이 배치인가**

- `08_데이터/raw/`를 분리한 이유: 원본을 임의 보정하지 않기 위해서다(응답 금지 항목).
- `_scratch/`를 분리한 이유: 검증 스크립트는 **재검증 근거로 남겨야 하지만** 고객사 공유드라이브에는 올리면 안 된다. `/sync-drive`가 자동으로 제외한다.
- 번호 접두어(`01_`~`99_`)는 탐색기 정렬 때문이다. `meetRecord/`만 번호가 없는 건 기존 관행을 그대로 둔 것.

### 6-2. 플러그인 저장소 (이 repo)

```
.claude-plugin/
  plugin.json                  # 플러그인 매니페스트
  marketplace.json             # 이 저장소를 마켓플레이스로도 쓰기 위한 설정
skills/                        # 해당 작업을 할 때만 로드된다
  wbs-progress/SKILL.md
  requirements/SKILL.md
  task-fieldcheck/SKILL.md
  db-review/
    SKILL.md
    references/dbms-notes.md   #   └ DBMS 방언 차이. DBMS 확정 후에만 읽힌다
  smartfactory-domain/SKILL.md
  data-analysis/SKILL.md
  email-draft/SKILL.md
  meeting-notes/SKILL.md
  doc-review/SKILL.md
  risk-register/SKILL.md
commands/                      # 명시적으로 실행하는 루틴
  init-project.md              # /init-project
  sync-drive.md                # /sync-drive
  weekly.md                    # /weekly
templates/                     # 프로젝트로 복사되는 것들
  CLAUDE.md
  PROJECT.template.md
  personal-profile.example.md  # → ~/.claude/CLAUDE.md 로
```

## 7. 일상 사용법 — 하루·한 주 흐름

### 7-1. 모듈 코드를 붙이지 않는다

v2에서는 `[M04] 이 쿼리 리뷰해줘`처럼 모듈을 직접 지정해야 했다.
**v3에서는 필요 없다.** skill의 `description`을 보고 자동으로 걸린다.

```
> 이번 주 진척 정리하고 지연 구간이랑 CP 영향 알려줘        → wbs-progress
> 이 요구사항 문장 모호한 부분 잡고 인수 기준 만들어줘        → requirements
> 아래 논의에서 할 일 뽑아서 우선순위 매겨줘                 → task-fieldcheck
> 이 테이블이 정말 대상 라인 데이터인지 검증 쿼리 짜줘        → db-review
> 이 문제에 AI가 정말 필요한지부터 검토해줘                  → smartfactory-domain
> 이 데이터 진단부터 하고 분석 방향 제안해줘                 → data-analysis
> 고객사에 일정 지연 통보 메일 초안. 온건/명확 두 버전        → email-draft
> 클로바노트 텍스트야. 회의록 + Task 정리하고 문서 반영해줘   → meeting-notes
> 이 문서 목차·그림·표·페이지 번호 전부 검수해줘             → doc-review
> 이 이슈 사실/영향/원인/조치/필요지원으로 정리해줘           → risk-register
```

자동으로 안 잡히면 `/db-review` 처럼 직접 호출해도 된다.

### 7-2. 현장 다녀온 날

```
> 클로바노트 텍스트야. [붙여넣기]
  회의록 만들고 Task 뽑고, 일정·범위 영향 있으면 요구사항정의서랑 WBS에 반영해줘
```

`meeting-notes`가 하는 일:

1. STT 오류 처리 — 설비·사람 이름은 **교정하지 않고** `⚠️확인필요`로 남긴다 (오인식이 잦아서)
2. **결정사항 / 논의만 된 것**을 엄격히 구분 — 애매하면 미결로
3. Action Item을 `task-fieldcheck` 포맷으로 추출
4. 일정·비용·범위 언급은 **CR 대상 여부까지 판단**
5. 요구사항정의서·WBS에 **바로 반영하고 반영 위치를 밝힌다** (즉시 반영 원칙)

### 7-3. 금요일

```
/weekly
```

WBS 진척 갱신 → 지연 식별·귀책 분류 → Task 재정렬 → 미결사항 팔로업 →
리스크 등록부 갱신 → 주간보고 메일 초안 → 공유드라이브 동기화까지 한 번에.

**메일은 초안만 만들고 멈춘다.** 발송·전달·캘린더 초대는 예외 없이 확인 후에만 실행한다.

### 7-4. 세션 끝낼 때

```
/sync-drive
```

- 파일명이 달라도 같은 문서면 → 드라이브 쪽 파일명 유지, 내용만 갱신
- `.gsheet` 같은 실시간 협업 문서 → **절대 로컬 파일로 덮어쓰지 않는다**
- `_scratch/`, `.env` → 제외
- 애매한 파일이 생겼을 때만 물어본다. 나머지는 묻지 않고 규칙대로 실행한다.

### 이 skill들이 실제로 막아주는 것

내용 대부분은 실제로 사고가 난 뒤에 추가된 규칙이다.

- **문서 불신 원칙** — 문서상 대상 라인 테이블이 실제로는 전혀 다른 라인 데이터였다. IP 정의서의 메인/서브 칠러가 실물 배선과 반대였다. → `db-review`가 쿼리 전에 `SELECT DISTINCT {라인식별컬럼}` 검증을 먼저 시킨다.
- **DBMS 미확인 상태로 쿼리 금지** — `TOP` vs `LIMIT`, `CHARINDEX` vs `POSITION`, 날짜 함수가 전부 다르다.
- **STT 이름 교정 금지** — 설비·회사·사람 이름은 오인식이 잦은데, 그럴듯하게 교정되면 잡아내기 어렵다.
- **인수 기준 누락이 검수 분쟁 1위** — `requirements`가 없으면 초안을 만들어서라도 채운다.
- **AI 과제는 [1] 데이터 진단 게이트에서 대부분 좌초** — `smartfactory-domain`이 AI 없는 해법을 먼저 검토시킨다.

`PROJECT.md` §11에 적는다. **여기 적힌 것이 `CLAUDE.md`와 skill보다 우선한다.**

이 저장소를 fork 하거나 clone 해서 `skills/*/SKILL.md`를 고치고, 로컬 경로로 마켓플레이스를 등록한다.


`description`에는 **본인이 실제로 쓸 법한 표현**을 넣어야 자동 라우팅이 잘 걸린다.

## 10. 민감 정보 취급

- **값이 채워진 `PROJECT.md`는 이 저장소에 커밋하지 않는다.** 고객사명·예산·이해관계자·DB 스키마 검증 내역이 들어간다.
- 프로젝트별 저장소를 따로 만든다면 반드시 **Private**으로. `.env`, `PROJECT.md`, DB 덤프, 회의록은 `.gitignore`에 넣거나 애초에 커밋하지 않는다.
- **이 플러그인 저장소에는 어떤 고객사명도 들어가지 않는다.** 예시는 `<설비명>` 같은 플레이스홀더로만 쓴다.
- `.env`는 **키 이름만** 읽는다. 값은 대화·산출물·회의록·커밋 메시지에 옮겨 적지 않는다.
- 고객사/현장 DB는 읽기전용(SELECT). DDL/DML은 명시적 승인 없이 실행하지 않는다.

## 11. 트러블슈팅

**skill이 자동으로 안 걸린다**
→ `/wbs-progress` 처럼 직접 호출한다. 자주 그러면 해당 `SKILL.md`의 `description`에 본인이 쓰는 표현을 추가한다.

**`/init-project`가 템플릿을 못 찾는다**
→ `${CLAUDE_PLUGIN_ROOT}` 해석이 안 되는 경우다. `/plugin`에서 설치 경로를 확인해 알려주면 그 경로로 복사한다.

**`CLAUDE.md`가 적용되는지 모르겠다**
→ Claude Code는 작업 디렉터리와 **상위 경로**의 `CLAUDE.md`를 세션 시작 시 자동으로 읽는다. 하위 폴더에서 실행해도 상위 프로젝트 루트의 것이 걸린다.

**`PROJECT.md`에 `<TBD>`가 너무 많다**
→ 그대로 둬도 된다. 그 정보가 필요한 작업을 할 때 그때 묻는다. 한 번에 채우고 싶으면 `/init-project`를 다시 실행하면 `<TBD>`만 골라 재질문한다.

**여러 프로젝트에서 규칙이 섞인다**
→ 고유 값이 `CLAUDE.md`에 들어간 경우다. 프로젝트 고유 정보는 전부 `PROJECT.md`로 옮긴다. `CLAUDE.md`는 모든 프로젝트에서 동일해야 한다.

**Windows 한글/대괄호 경로에서 스크립트가 멈춘다**
→ `db-review`의 실행 환경 함정 절 참고. 대괄호 경로는 PowerShell `-LiteralPath`, 큰 스크립트는 `python -c` 대신 `.py` 파일로, 콘솔 출력이 cp949로 깨지면 UTF-8 파일로 덤프 후 읽기.

## 12. 설계 원칙 · 유지보수

### 무엇을 어디에 두는가

**로드되지 않은 skill은 아무것도 제약하지 못한다.** 그래서 제약을 skill로 빼면 안 된다.

| 성격 | 예시 | 위치 |
|---|---|---|
| 항상 켜져 있어야 하는 **제약** | 협업 원칙 7개, 응답 금지, 산출물 포맷, 보안 | `CLAUDE.md` |
| 요청 시 꺼내 쓰는 **절차** | WBS 구조, 쿼리 리뷰 체크리스트, 회의록 포맷 | `skills/` |
| 명시적으로 실행하는 **루틴** | 온보딩, 동기화, 주간 점검 | `commands/` |
| 개인·프로젝트 고유 **값** | 프로필 / 고객사·경로·KPI·접속정보 | `~/.claude/CLAUDE.md` / `PROJECT.md` |

산출물 포맷 규칙("트래킹형 문서는 xlsx")과 보안 규칙("DDL 무단 실행 금지")을 skill로 빼면
그 skill이 호출될 때만 적용된다. 명백한 후퇴다. 그래서 `CLAUDE.md`에 남겼다.

### 유지보수

- 프로젝트가 끝날 때마다 새로 배운 실패 패턴을 `risk-register`의 상시 리스크 또는 해당 skill에 추가한다. **한 번 고치면 전 프로젝트에 반영된다.**
- 고객사·시스템 고유 규칙은 이 저장소가 아니라 `PROJECT.md` §11에 넣는다.
- skill 본문이 비대해지면 `references/` 하위로 분리한다(`db-review` 참고). 본문은 짧게, 세부는 필요할 때만 로드되게.
- `description`은 사용자가 실제로 쓸 법한 표현을 넣어야 자동 라우팅이 잘 잡힌다.
